# Bug 1 on phase-06: the tail-copy test does not exercise the tail-copy path

**Severity:** blocker
**Status:** open
**Filed:** 2026-08-04

## What's wrong

`compact_preserves_bytes_appended_during_the_run` (`mcp/src/compact.rs:641`)
performs its "concurrent" append **before** calling `compact_store`:

```rust
        // Simulate concurrent append: add a stamped run after the initial content.
        let appended = format!("{}\n", stamped_run_line());
        let mut file = fs::OpenOptions::new().append(true).open(&store).unwrap();
        file.write_all(appended.as_bytes()).unwrap();
        drop(file);

        let args = CompactArgs { /* ... */ dry_run: false };
        let outcome = compact_store(&args).unwrap();
```

By the time `compact_store` runs, those bytes are already part of the file, so
`fs::metadata(&store_path).len()` counts them in `initial_len` and they are
selected by the ordinary §2 rules. The tail-copy loop never executes. The
assertion `assert!(outcome.output_lines >= 2)` is also a `>=`, which cannot
distinguish the two paths even in principle.

**Proven by mutation.** Deleting the entire Phase-3 tail-copy block
(`mcp/src/compact.rs:118`–`:139`, from `// Phase 3: tail-copy` through the loop)
and re-running the suite:

```
test result: ok. 13 passed; 0 failed; 0 ignored; 0 measured; 697 filtered out
```

All 13 tests pass — including this one — with the feature it names removed
entirely.

This is the phase's **concurrency guarantee**. §3 of the spec makes tail-copying
the reason the user does not have to stop `rexymcp serve` before compacting, and
the module doc comment advertises it. Right now nothing verifies it works, and a
regression that silently drops every record appended during a compaction would
ship green.

## What should happen

The test must fail if the tail-copy loop is removed. The phase doc's Test plan
named this and gave two acceptable routes:

> Simulate by appending to the store between the length-stat and the tail copy;
> if that is awkward to inject, restructure so the tail copy is a separate
> testable function and test it directly.

Neither was taken. Take one of them.

## How to fix

In `mcp/src/compact.rs`, pick whichever is cleaner:

**Option A — extract and test directly.** Pull the Phase-3 loop into a private
`fn copy_tail(store_path: &Path, tmp: &mut fs::File, from: u64) -> Result<u64, String>`
and call it from `compact_store`. Then test `copy_tail` on its own: build a file,
record a length, append after that length, call `copy_tail`, and assert the
appended bytes landed in the temp file verbatim.

**Option B — inject the append at the right moment.** Give `compact_store` a
test-only seam (e.g. a `#[cfg(test)]` callback invoked after the length-stat and
before the tail copy) that appends to the store, then assert the appended record
survives into the compacted output.

Either way the new/reworked test must use a **strict** assertion on the appended
record's presence (`assert!(output.contains(...))` plus an exact expected line
count), not `>=`.
