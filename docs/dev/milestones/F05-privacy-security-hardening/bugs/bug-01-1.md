# Bug 1 on phase-01: `expect()` in a production path in `LiteralTerms::mask`

**Severity:** minor
**Status:** fixed (c1579cf)
**Filed:** 2026-09-17

## What's wrong

`executor/src/privacy/terms.rs:150`, inside `LiteralTerms::mask`, which runs on
every outbound message:

```rust
        for caps in regex.captures_iter(text) {
            let m = caps.get(0).expect("the whole regex matched");
```

`STANDARDS.md` §1 requires "No new `unwrap()` / `expect()` / `panic!()` in
production paths (test code is exempt)", and §2 (the error model) says the same.
Line 150 is production: the test module starts at line 174.

It is the only new production-path panic in the phase. The `expect` at
`mcp/src/runner.rs:466` is pre-existing, from commit `b9f1c97`.

Everything else in this phase passes. The architect's independent re-run:
fmt/build/clippy clean with zero warnings, `cargo test` 716 + 2 + 1188
(10 ignored), all 14 tests the Test plan names are present, and a mutation
check confirms they bite — dropping the left `\b` from the alias pattern fails
`default_entry_requires_both_boundaries`, `embed_entry_matches_inside_an_identifier`
and `loads_entries_and_flags`.

## What should happen

`mask` masks without a panic path. Capture group 0 of a match from
`captures_iter` is always present, so the claim is true today — but the rule
exists because such claims rot, and this one sits on the egress chokepoint,
where a panic would take down a dispatch mid-flight.

Any panic-free form is fine. `regex.find_iter(text)` yields the same `Match`
values directly, and `matched()` would then need the `Captures` only for
picking the code — or `let Some(m) = caps.get(0) else { continue };` keeps the
current shape.

## Root cause

`captures_iter` yields `Captures`, whose `get(0)` returns `Option<Match>` even
though group 0 always matched. The executor reached for `expect` to discharge
the `Option` instead of a `let else`.
