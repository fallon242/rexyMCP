# Bug 1 on phase-01: `rexymcp init` template omits `[governor] read_only_stall_threshold`

**Severity:** minor
**Status:** open
**Filed:** 2026-07-24

## What's wrong

Phase-01 added `GovernorConfig::read_only_stall_threshold` (`executor/src/config.rs:247`,
default `60` at `executor/src/config.rs:278`) — the `NoProgressStall` backstop and,
after M37 phase-01 exempted non-mutating windows from the oscillation /
identical-call detectors, **the sole volume backstop for read-only runs** (README.md:883
says exactly that). It never reached the `rexymcp init` config template.

`mcp/src/init.rs:37-45` emits a `[governor]` block with seven keys:

```toml
[governor]
identical_call_threshold = 6
verifier_persistence_threshold = 6
runaway_output_bytes = 102400
oscillation_window = 8
oscillation_distinct_max = 2
output_window = 6
output_window_bytes = 262144
novelty_action = "advisory"
```

`read_only_stall_threshold` is absent. The value still applies — `#[serde(default)]`
falls back to `60` — so behavior is correct, but a new project's generated
`rexymcp.toml` gives no sign the knob exists. That matters more here than for a
typical default: README.md:883 tells the user to tune it per-model against
`calibrate-governor`'s `max_read_only_run` distribution, and the template is where
that tuning would land.

Precedent inside this same milestone: phase-05 §4 ("`rexymcp init` template")
explicitly required its new knob be added to the block, and `novelty_action` is
there. Phase-01 (and phase-03, below) had no equivalent step.

`init_writes_parseable_config` (`mcp/src/init.rs:137`) asserts three governor
defaults round-trip, and passes with the key missing — a parse-level test cannot
catch a template omission.

## What should happen

Every governor knob the user is expected to tune appears in the generated
template, as a live line or a commented one, consistent with how `novelty_action`
is treated. At minimum `read_only_stall_threshold = 60` is present in `[governor]`
with a comment naming its role (read-only backstop, resets on any mutating call,
`0` disables), and the per-model override list at `mcp/src/init.rs:55-61` gains the
matching commented `# read_only_stall_threshold` line — `ModelOverride` already
supports it (`executor/src/config.rs:307`), and README.md:899 documents the
per-model form.

## How to fix

1. `mcp/src/init.rs` — in `generate_config`'s `[governor]` block, after
   `output_window_bytes`, add:

   ```toml
   read_only_stall_threshold = 60    # consecutive non-mutating tool calls → hard-fail; resets on any patch/write_file (0 disables)
   ```

2. `mcp/src/init.rs` — in the commented `[models."<model-id>"]` block, after
   `# output_window_bytes = 524288`, add:

   ```toml
   # read_only_stall_threshold = 30     # override [governor] read_only_stall_threshold
   ```

3. `mcp/src/init.rs` tests — extend `init_writes_parseable_config` with
   `assert_eq!(cfg.governor.read_only_stall_threshold, 60);` and add a test that
   the rendered template *text* contains the key, so a future omission fails
   rather than silently inheriting the serde default.

## Notes for review (not in scope of this bug's fix)

The same phase-01/phase-03 gap leaves three further `GovernorConfig` fields out of
the template: `novelty_window` (24), `novelty_distinct_floor` (6), and the older
`empty_completion_threshold` / `gate_feedback_repeat_threshold`. `novelty_window`
and `novelty_distinct_floor` are the tunable pair behind `novelty_action`, which
*is* templated — documenting the action but neither of its thresholds is the
oddest of these. Whether to template all of them (and whether the per-model list
should mirror the full override set) is an architect call, not this bug's.
